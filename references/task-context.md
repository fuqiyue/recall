# 任务上下文

权威语义见宪法 RULE-027 与工具链 RULE-028。这里只说明使用方式。目标是让下一位模型知道需求来源、目前有哪些任务和剩余工作；正文可简短自然表达，无需额外的固定推理步骤。

## 想法与已决定的待办

在根 `logic_change.md` 按需添加 `## 待办` 表。根公报只索引 CHG，待办由 `recall next` 跨账本汇总。启动后正文放 `logic_changes/<任务>/logic_change.md`；同任务的计划、进度、变更说明及产物台账在同一文件更新，见[工作路径与任务](workspace-tasks.md)。没有待办就不用创建空表。

```markdown
## 待办

| task_id | stage | context | source_ref | next_action |
|---|---|---|---|---|
| TASK-search | idea | 用户在考虑按任务搜索；使用场景尚未确定 | user:2026-09-07 讨论 | 对照现有 route 说明差距 |
| TASK-handoff | planned | 已决定改善接手；成功时能看出每项剩余动作；保持现有账本 | user:2026-09-07 决定 | 结合本次任务选择首个可验证成果 |
```

`task_id` 在项目内唯一；`idea` 表示提出想法，`planned` 表示已决定要做但还未开始。`context` 保留目标、重要限制和已知完成条件；未知项直接写未知，不强制补齐清单。单元格中的竖线用 `&#124;`。

开始时，simple 按任务直接执行；需要 CHG 则把来源、关键上下文和验收条件承接到 CHG，再移除待办行。idea 的提出来源不能自动变成实施授权；planned 的来源也不承诺本次必须执行。用户明确要求立即实施时直接沿用该授权，不先制造一轮待办或重复确认。

大目标可拆成独立可验证的成果，各成果写清用户能观察到的结果。只有可独立交付和回滚才拆多个 CHG，否则在一个案内列步骤。未采纳的普通想法可移除；已正式作出的设计决策仍按生命周期保留理由。

## 接手与阻塞

运行 `recall next`（机器消费可加 `--json`）。读取候选的 `path` 指向的完整需求、证据和约束，再判断下一步。类别只是账本状态的保守投影，没有固定优先级分数、并行数量或强制周期。

CHG 可用以下既有/轻量字段补足接手信息；只在信息有用时写，缺项提示不构成新审批门：

```markdown
- next_action: 解除文件占用后清理本次临时目录
- blocked_by: external:file-lock
- blocked_reason: 删除失败，进程仍持有句柄（附错误证据）
- owner: Codex
- review_due: event:占用进程退出
```

`next_action` 可用于任何阶段；阻塞时它应说明解除动作，`owner` 是执行该动作的责任方，复查时机可写日期或事件。既有 `unblock_condition` 可继续提供解除判据。视图不轮询、不发通知、不自动执行或修改状态。

视图区分收尾、进行中、可做候选、待决策、阻塞、待核对、想法。依赖目标仍活跃就显示阻塞；依赖目标缺席或已改绑 VER 时提示模型重核基线，不自动认定完成。冲突关系、缺少决定来源、未知状态与重复 ID 保留不确定性。`promoting` 项仍有真实阻塞时优先显示阻塞。

## 公报与一致性

`recall index` 从全部已登记账本的 CHG 正文生成根公报，显示候选表并检查一致性；差异退出 1，不修改文件。`recall index --write` 只更新根公报表与根文档控制的 `active_changes`（根 CHG 正文数，不是全项目数）。待办不计入 CHG 数量。

先检查输出再按需要写入。未知表头或重复 ID 会拒绝写入，避免覆盖人工正文；其他段落和领域账本不写。公报是派生索引，修改任务请编辑所属正文再生成公报。日期取正文的 `last_updated`、`last_status_change` 或决定日期，不伪造本次复核日期。

运行 `recall validate` 与 `recall audit` 核查规则、链接、生命周期和实际产物，关案前运行 `recall workspace --closing CHG-ID`。公报一致不代表通过审查。旧 CHG 继续兼容；按任务迁移时保留ID、移动正文并改公报/历史草稿/临时台账回链。
