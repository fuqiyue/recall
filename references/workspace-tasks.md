# 工作路径与任务账本

规则来源：根 RULE-018/020/027/029。按本文设置路径、盘点文件或管理任务；不用另建 PLAN、STATUS、HANDOFF 正文。

## 项目根与文件地图

用户指定的项目文件夹就是根。根 `logic_readme.md` 声明以下字段；存量项目省略时取默认值：

```markdown
- workspace_root: .
- scratch_root: .work/
- data_roots: 资产库/; 下载记录/
```

`data_roots` 按项目实际填写；空项目用 `none`。现有功能目录保持原位，由领域 `owned_paths` 认领。正式源码、运行数据、交付证据的位置在所属代码地图说明，不因盘点而搬家。

1. 先 `recall inventory --json` 有界识别目录，再针对相关目录盘点，例如 `recall inventory content 资产库 --data-root 资产库`。
2. 算法按真实目录、文件扩展名和 `owned_paths` 生成简要说明。功能含义只是候选，不能由名称推断用户意图；不读取素材内容。
3. `--write` 合并到 `logic_domains/file_map.md` 总览，再派生领域地图。只替换本次完整列举目录的直接条目；确认消失的目录连同旧子树索引移除。未扫描、深度/数据边界及预算截断部分保留旧条目、时间和边界，不把“没扫到”当“已删除”。已有手写同名文件不会覆盖。
4. 地图本身保存逐目录覆盖、扫描时间、目标、深度、预算和未深入边界，无额外清单文件。旧版地图首次更新保留未重扫内容并注明覆盖未知。功能目录列文件；数据目录只列上层。截断时按目标分批查，不把抽样说成全量。

输出前运行 `recall path <项目相对路径>`，例如 `recall path .work/临时-修复目录索引/probe.py`。路径只在一个已解析的项目根上拼接一次；执行命令显式设置 cwd。工具拒绝绝对路径、`..`、盘符碎片、重复项目根和链接路径。旧文件先查来源和引用，不凭目录名自动删除。

## 一项任务，一个正文

```text
项目根/
├─ logic_readme.md                       全局现行规则与路径约定
├─ logic_change.md                       全项目活跃任务索引
├─ logic_domains/<领域>/logic_readme.md   领域现行规则
├─ logic_domains/<领域>/file_map.md       可重建文件地图
├─ logic_changes/<任务>/logic_change.md   需求、计划、进度、变更、产物台账
├─ .work/临时-具体功能/                   临时代码及其输出
└─ logic_version/                        records保留正式历史；pending_cleanup暂存待清理副本
```

立案前用 `next` 查看活跃任务，对照目标、约束与验收结果。相同或接近的需求能纳入同一目标、统一验收与收尾时，优先扩展已有 CHG 的需求和修订表，不因新一轮对话、多文件修改或名称不同另建正文。必须独立发布/回滚、授权冲突或验收互不相关时才分案关联；名称相似只是复核线索。关闭后的新需求另开任务并引用原 VER。

已有两个相近活跃案需要合并时，保留一个 CHG；将另一案的独有需求、授权来源、失败事实、修订及产物行去重搬入，修订行注明原 CHG/轮次，用 `merged_from` 保留原 ID。核对依赖、公报和草稿引用后移除重复正文及空目录，最终同一 VER 保全合并来源；不改已归档决定，也不复制两套计划。

根公报由 `recall index --write` 派生。`next/status/route/validate/audit` 都能发现任务文件；正文以 `scope/affected_scopes` 关联领域，跨领域任务也只有一份正文。新领域使用 `readme-only`，旧 `paired` 领域与根旧正文继续兼容；迁移时移动正文并更新引用，不复制一份。

`recall route CHG-ID` 或任务文件/目录路径先解析主 scope 与 affected_scopes（也接受登记的 module_id），再列所属规则；未知范围或重复 ID 明示告警。其他相关任务只列标题、状态及链接，必要时按 ID 再读，或使用 `--include-related` 展开。普通关键词仍是启发式。

## 多轮修订

按 RULE-027，正文顶部的 `status/current_result/next_action` 是唯一当前状态；其余章节只保留当前方案与依据。根公报派生标题、状态和链接；领域 readme 只更新已生效规则，不复制接手/进度段。旧计划收敛进一张修订表，详细结果仅链接必要证据。创建 CHG 时记首轮；一轮可覆盖多个文件，不逐条记录工具调用，也不创建 `v2.md`、`history.md` 或独立交接正文。

| 轮次 | 日期 | 方案版本 | 原因与修改 | 涉及文件 | 结果/验证 |
|---|---|---|---|---|---|
| 01 | 2026-10-20 | 1 | 示例：建立素材归档规则 | scripts/catalog.py | 基础场景通过 |
| 02 | 2026-10-20 | 2 | 示例：发现同名覆盖，调整命名规则 | scripts/catalog.py、tests/test_catalog.py | 重名场景通过 |
| 03 | 2026-10-20 | 2 | 示例：修复实现遗漏，方案不变 | scripts/catalog.py | 回归通过 |

- **轮次**按本任务的修改节点递增；**方案版本**对应 `proposal_revision`，仅方案、影响面或基线发生实质变化时递增。普通实现修复、补测不强制升版；仍须核对已有授权适用范围。
- 每行简记原因、变化、项目相对路径和真实结果；未验证写明。当前轮可以补充结果，已结束轮的关键事实保留，发现误记以新行注明纠正轮次和依据，不覆盖失败或被放弃的方案。
- 清理正文中失效的安排，保留表内变化原因。存量任务从本次接手开始记录，注明旧过程未记录或未核实，不补造轮次和验证结果。
- 按 RULE-025，关案将这张已精简的表连同需求搬入同一 VER 的“修订记录”，核对轮次、最终版本和结果；归档后的引用须仍可读取，已删临时证据改留结论。只保留一份历史，不逐轮生成 VER 或复制整个任务目录。没有 CHG 的 simple 修改不增加此流程。

## 临时产物与关案

任务正文加 `task_temp_dirs` 和同一张台账；没有临时代码填 `none`，不为凑流程创建空目录。中高风险任务保留空台账表以明确无新增产物，不再另建 `logic_temp.md`。

```markdown
- task_temp_dirs: .work/临时-修复目录索引

### 工作区产物台账
| path | artifact_kind | disposition | reason | cleaned_at | retention_basis | exit_condition | round |
|---|---|---|---|---|---|---|---|
| scripts/catalog.py | deliverable | keep | 正式功能 | - | 目录生成入口 | 功能退役时复核 | 01 |
| .work/临时-修复目录索引/round01/ | scratch | delete | 本轮探针与输出 | - | - | 本轮结束删除 | 01 |
```

- 路径相对于项目根；台账登记本次新增交付物和临时产物。删除整棵临时目录可登记目录一行，覆盖其内容。不得用整个项目、功能目录或数据目录作为清理目标。
- 临时代码及其输出统一进 `scratch_root/临时-具体功能`。任务间不共享该目录；同名功能用任务编号消歧。
- `artifact_kind` 区分正式交付物 `deliverable`、运行数据 `runtime-data`、正式证据 `evidence` 与临时物 `scratch/probe/...`。`keep` 必须写 `retention_basis`（消费者/规则/结论依据）及 `exit_condition`（移除或复核触发条件，长期保留也写依据）。整目录保留须有统一用途；用途或退出条件不同就拆行。数量、大小仅提示复核，不能作为删除依据。旧五列表仍可读，旧证据缺依据只告警，新扩展表缺依据报错。
- 每轮结束处理标有本轮 `round` 的产物：删除不再需要的临时文件；下一轮仍依赖的少量产物改归下一轮并在 reason 写明依赖与退出条件。按需用 round 子目录隔离；不逐轮创建新过程文档。可用 `recall workspace --task CHG-ID --round 01` 核对该轮台账，未登记轮次不报“已清理”。跨轮依赖最终也须在任务完成时退出。
- 可复用代码、运行数据与必要证据先放到正式位置，再删临时副本。任务完成后删除全部临时代码、输出及空目录；`.gitignore` 只影响 Git 可见性。旧任务/用户文件先核归属和引用，工具不自动删除。
- `workspace --task CHG-ID` 看本任务现状，`--closing CHG-ID` 按整案完成条件核实；返回 `task_result`、`global_result`、`other_findings`，带 `--round` 另有 `round_result`。原 `ok/findings` 仍表示全局，`selection_ok` 及 CLI 退出码按所选视图判断。其他任务遗留不冒充本任务失败，实际共享目录仍阻塞双方；不带筛选的 workspace 与 audit/validate 保持全局核对。
- 将必要结论写回 readme，需求、修订表及验证/清理事实归入同一 VER，登记历史索引并核对内容后，移除任务正文、公报行及空任务目录。旧任务 `logic_temp.md` 清零后删除，兼容期间不可重复维护两张台账。

Recall 不能拦截任意外部脚本的写文件行为；路径检查需在输出前使用。文件地图不是实时文件系统，扫描边界必须如实说明。现有 CLI 核对结构、索引及产物；修订记录的完整性与归档一致性由执行代理核对，不宣称工具已自动验证其语义。

## 核验后逐项删除

按 RULE-020/025，优先实际清理；已移入待清理区的副本也使用以下顺序，不为清理另建任务或报告。

1. **核验**：确认文件归属、引用及退出条件；解析准确绝对路径，核目标与父路径位于指定项目内且无链接/重解析点。已归档重复正文须核任务身份、需求/修订/必要证据已完整归档、无未完事项；记录源与正式归档的 SHA256，已有待清理登记须匹配原指纹。普通临时物核现有台账即可，不另建指纹清单。
2. **所需权限走正式审批**：已有业务授权沿用；目标超出可写工作区或环境要求审批时，提交准确路径、操作和核验依据，获准后执行。审批仍拒绝或环境不提供审批时，按下节判断兜底；无新证据不反复重试，不更换工具规避拒绝，也不放宽安全设置。仅返回 `blocked by policy` 时照实说明，不能猜测具体拒绝原因。
3. **逐项删除**：使用原生文件操作；Windows 用 PowerShell `Remove-Item -LiteralPath <已核验的绝对路径> -ErrorAction Stop`，文件与目录分别处理。仅删除已用 `Get-ChildItem -LiteralPath <目录> -Force` 确认为空的具体目录；不使用通配符或递归删除代替核验，不跨 shell 拼接命令。执行前若文件/指纹变化，先重新核验。
4. **核实结果**：确认目标实际消失、正式归档指纹与其他任务未变，再移除对应待清理行；目录仍残留就保留该行说明。运行 `recall workspace --json`、`recall next` 和 `recall index`，公报确需更新才用 `index --write`。区分本次结果与全局遗留；不改定稿 VER，不在 change 正文追加清理经过。

## 删除受阻的集中待清理

完成上述核验与所需审批后仍受限（或环境不提供审批），才考虑此出口。仅适用于独立任务已交付、需求/修订/必要证据已完整归入定稿VER并登记索引、其余临时产物已处置的重复正文；不适用于现行规则、正式代码、运行数据、唯一证据或整个任务目录，混合账本不整本搬走。

1. 保留删除/审批失败的真实原因，判断保全移动是否是执行策略允许的较安全替代；移动所需权限同样走正式审批。拒绝若涉及移走源文件或要求原位保留，不得移动、复制后清空或伪装操作。移动也受限时保持原文不动，按第3步在历史索引登记“原位待清理”，不在change正文追加说明，也不新建清理任务。
2. 核定项目内两个准确路径、无链接、目标不存在、没有并发写者。记录源文件SHA256，用原生文件移动将正文移至 `logic_version/pending_cleanup/<CHG-ID>/logic_change.md.txt`；内容原字节保留，`.txt`表明冻结副本，其旧相对链接按原路径理解，不再当现行正文解析。移动前后指纹相同且原路径消失才算保全成功；不覆盖同名目标，不递归搬走其他内容。仅删除确认已空且获允许的原任务目录，空目录删不了则记录原路径待处理。
3. 在现有 `logic_version/index.md` 增加下表，路径均相对项目根（使用文本路径，不给已消失的源路径造链接）。`allowed_children` 加 `pending_cleanup`。每份副本一行，不另建计划、交接、删除报告或每轮备份；不修改已定稿VER。

```markdown
## 待清理文件
| task_id | original_path | path | archive | sha256 | reason | recorded_at | exit_condition |
|---|---|---|---|---|---|---|---|
```

`task_id` 填原CHG；`original_path` 填原独立正文；`path` 在移动成功时填上述待清理路径；若移动也受限，填与original_path相同的原文件路径，reason明确“原位待清理，内容已归档，允许时可删除”；`archive` 填 `logic_version/records/` 下对应定稿文件（须以change_id/proposal_id回链该CHG）；`sha256` 填登记时源文件完整指纹；`reason` 记真实失败及处置依据；`recorded_at` 记实际登记日期；`exit_condition` 写“执行策略允许后复核归档与指纹，删除副本及空目录”。原空任务目录仍存在时也在reason/exit_condition中记明，不能称全部清理完成。

4. 原位待清理只对唯一登记、对应定稿归档、任务身份及SHA核验通过的独立正文生效。旧文件不再解析为活跃任务；其字节变化、登记歧义或归档失效时立即恢复发现并报错，防止隐藏新工作。状态只在历史索引维护，冻结正文不追加阻塞解释。

运行 `recall index --write`、`recall next` 和 `recall workspace --json`。确认旧任务退出活跃公报、其他任务未变；workspace只读核对指纹、存放位置、正式归档和未登记文件；移动成功须源路径消失，原位登记则须源文件保持指纹一致。合法待清理项是warning，异常项是error；`pending_cleanup.cleanup_complete=false` 表示仍有清理欠账，结构通过不等于删除完成。不因这一项重新执行已完成业务。
5. 后续统一处理仍按[核验后逐项删除](#核验后逐项删除)执行；再次受限就保留同一行、更新原因。没有待清理项时不创建空目录。

副本需要进入Git时，在项目 `.gitattributes` 中用 `logic_version/pending_cleanup/** -text` 保留原字节，并核Git blob指纹；不让跨平台换行转换破坏SHA。原位正文若因检出/编辑发生字节变化，仍须重新核对归档与实物，不自动放宽指纹门。
