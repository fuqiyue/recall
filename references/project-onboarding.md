# 项目接入流程（新项目与存量项目）

`recall init` 只负责 Git 管道（仓库、身份、自动同步、hook）。本文档回答它不回答的问题：
**logic_readme.md 的内容从哪来** —— 尤其是已有大量代码的存量项目。

**核心策略：模块化渐进接入。** 不做一次性全量扫描；先建宪法骨架加至少一个领域（RULE-018 一二级拆分法），之后按模块补全。
文档补全只在两种时机发生：

1. **接入时（新项目开始使用 Recall）**：建立宪法骨架 + 首个领域 + 主流程初稿（见下"第一步"）
2. **用户单独要求时**：用户点名某个模块或功能，才补全对应条目

此外，按 SKILL.md 核心原则 6（docs_impact）：修改触及尚未登记的模块时，在同一获授权
变更中顺带补齐该模块的登记条目——这是既有规则的自然结果，不是额外流程。

**不允许的做法**：为"补文档"擅自创建未登记的 `logic_domains/*` 或其他子级 logic 文档（违反
INV-001/INV-002 与核心原则 3；合法做法见下"领域划分与拆分"——登记表行与领域文件在同一变更中一起落地）；
未经用户确认就把 AI 推断的功能意图标注为已确认。

---

## 第一步：宪法骨架 + 首个领域（接入时，一次性）

在 `recall init` 之后，按 [logic_readme 模板](logic-readme-template.md) 建立**最小**根文档（宪法），并按
[领域文档模板](logic-domain-template.md) 建立至少一个领域：

1. **文档控制 + 目标与边界**：项目是什么、负责什么、不负责什么（问用户，一句话级别）
2. **范围登记表（领域目录）**：先登记至少一个 `paired` 领域行——小项目用一个
   `logic_domains/core/` 覆盖全部代码即可，`owned_paths` 写顶层代码目录；再列其余顶层
   模块目录，每行只需 `module_id`、`scope_path`、`status`，尚未补全文档的登记为
   `status: pending-docs`，让"哪里还没有文档"本身可见。随后创建
   `logic_domains/<domain>/logic_readme.md` + `logic_change.md`（模板字段填齐，规则表可空）
3. **代码地图**：写在拥有该路径的领域文档；只填已识别的顶层入口（主入口文件、配置、测试目录），职责一句话；
   AI 从代码扫描得出的描述在"权威来源/决策依据"处标 `code-derived`，与用户确认的条目区分
4. **功能意图层初稿**（只写在宪法）：访谈式提问从用户口中提取（不从代码反推）：
   - "这个项目的用户是谁？他们用它完成什么？"（→ 3~8 条 INT）
   - "用户从打开到完成一件事的典型顺序是什么？"（→ 1~3 条 FLOW）
   - "哪些操作习惯绝对不能破坏？"（→ UXI，可为空）
5. **不变量与当前限制**：只写用户明确说出的约束，宁缺毋滥

产出以用户确认为生效条件：骨架落盘前把 INT/FLOW 初稿念给用户听，确认后写入。每条 INT 的 `来源` 列如实标注：用户原话转写填 `user:日期`，AI 起草经确认填 `user-confirmed:日期`，尚未确认的填 `inferred` 或 `code-derived`（validate 告警，直到用户确认）。用户的表述就是宪法的来源；此后用户每次提出新目标或约束，先对照意图层，没有就先立修宪案登记再做领域工作。落盘后跑
`recall validate` 与 `python scripts/audit_logic_map.py . --current-state`，Density 段不应再出现
`constitution-without-domains`。

## 第二步：模块补全（按触发时机，每次一个模块）

对触发补全的模块 `<scope_path>`：

1. **扫描**：AI 读该模块代码与测试，起草代码地图行（路径、职责、输入/输出、关联测试）
2. **访谈**：向用户确认两件事——该模块服务哪个用户目标（复用/新增哪条 INT）、
   位于哪条 FLOW 的哪一步；用户说不清时按核心原则 5 记为待澄清项，不硬填
3. **落盘**：用户确认后：
   - 宪法范围登记表该行 `pending-docs` → `active`；该模块归入某领域 `owned_paths`（不单独成领域时可在领域文档加稳定锚点小节 `<a id="scope-...">`），或按下节新建领域
   - 拥有该路径的领域文档加规则行、代码地图行与测试行；宪法的 INT/FLOW/UXI 增改对应条目（编号用 `INT-YYYYMMDD-NNN` 完整格式）
4. **验证**：`recall validate`（意图层引用与锚点检查）+ `python scripts/audit_logic_map.py . --current-state`

单模块补全属于中等变更以下的文档工作，不要求 CHG/VER；一次性补全多个模块或
借机调整制度时按三条通道正常分流。

## 领域划分与拆分（RULE-018）

宪法只放全局层，领域（部门法）承载各自职权路径的规则、代码地图与测试。大部门制：规则少时
一个领域兼管多项职责；领域长大后拆成更小领域。**划分由 AI 建议、用户决定**：AI 在审查或
修改中发现触发信号时提出建议并说明理由，用户确认后才实施。

**触发信号**（示例，非硬阈值）：领域 readme 越过目标 250 行（Density `over-target` 提示）且
压缩后仍不足；某组规则/代码地图行明显聚集为一块独立职权；模块有独立的发布节奏或团队边界。
反向信号（合并）：两个领域规则都很少且职权路径总是一起改。

**新建/拆分步骤**：

1. 用户确认新建或拆分哪个领域，以及它接管的 `owned_paths`
2. 按[领域文档模板](logic-domain-template.md)创建 `logic_domains/<domain>/logic_readme.md`
   与 `logic_change.md`（`module_doc_policy: paired`，`parent: ../../logic_readme.md`）
3. 在根 `logic_change.md` 立修宪案（登记表行属宪法内容），把领域行加入宪法范围登记表：
   `| MOD-<NAME> | logic_domains/<domain> | in-system | domain/runtime-code | paired | ... | ... | self | active |`
4. 把该职权范围的规则行、代码地图行、测试行迁入新领域文档（拆分时从原领域迁出并收窄其
   `owned_paths`）；宪法只保留全局规则、INT 层与该领域的目录行（一句话职责即可）。迁入时给
   代码地图补 `contract_class` 列（`public`/`persisted`/`security`/`internal`）：这是 SKILL
   "路由一问"的靶子，缺列时每次通道判定都要人工判断"有没有外部调用方"
5. 引用旧锚点（`#scope-...`）的活跃 CHG 改为引用 `MOD-ID`；原领域账本中只涉及迁出路径的
   CHG 随正文迁到新领域账本，公报行同步改 `proposal_path`
6. 跑 `recall validate` + `python scripts/audit_logic_map.py . --current-state` 确认编号唯一、
   公报一致、路由对账通过；再用 `recall route <迁入路径>` 确认命中新领域

**划分后的阅读与修改顺序**：改某领域 = 读宪法（全局规则 + 领域目录）→ 读根 `logic_change.md`
（修宪案 + 公报）→ `recall route` 命中的领域 readme + change → 代码/测试；跨领域变更 = 读全部
相关领域文档，并在同一变更中一起更新。宪法优先于部门法。`logic_change.md` 每级一份（根账本
放修宪案与公报，领域账本放本领域正文）；`logic_version/` 不拆分，全项目始终只有根一份。

## 存量项目的节奏建议

- 接入当天只做第一步，控制在半小时内；价值从第一次"改代码前先读文档"就开始兑现
- 优先补全的模块 = 近期要改的模块（git log 热点），而不是按目录字母序；接入当天一个
  `core` 领域够用，等它越过目标行数再拆
- `pending-docs` 长期存在是正常状态：没被改动的模块不欠文档
