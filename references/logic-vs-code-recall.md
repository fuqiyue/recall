# 逻辑回档 vs 代码回档

**Recall 的核心理念：保存设计逻辑，而非代码快照。**

## 基本区分

- ❌ **不是代码回档**：不保存完整历史代码、不维护多版本代码快照、不记录每次的代码变化
- ✅ **而是逻辑回档**：保存"为什么这么设计"的推理过程、关键取舍、影响分析
- 🎯 **目的**：需要时可以**重新理解设计思路**，避免"按下这头翘起那头"

## 为什么这样设计？

1. **避免上下文爆炸**：完整历史代码会让文档迅速膨胀，AI 无法有效读取
2. **Git 已经负责代码版本**：代码回档交给 Git，Recall 只负责"为什么"
3. **重点是防止设计退化**：修改时需要知道"当初为什么这么做"，而不是"当初代码长什么样"

## 历史记录保存什么？

`logic_version/records/` 中的 `logic_version-*` 记录保存：

**✅ 保存（轻量）：**
- 为什么做这个决策？（设计原因）
- 考虑过哪些方案？（A/B/C 对比）
- 为什么选择当前方案？（取舍分析）
- 影响了哪些消费者？（影响范围）
- 如何验证和回滚？（验证方式）

**❌ 不保存（避免膨胀）：**
- 完整的代码快照
- 逐行的代码变更 diff
- 详细的实现细节
- 原始对话记录（太长）
- 思维推理过程（隐藏思维链）

## 示例对比

### ❌ 错误方式（代码回档）

```markdown
## VER-20260807-001: 添加用户认证

### 代码快照
\`\`\`javascript
// 保存 500 行完整代码...
function authenticate(user, password) { ... }
\`\`\`

### 代码变更
\`\`\`diff
+ line 1: import jwt from 'jsonwebtoken'
+ line 2: import bcrypt from 'bcrypt'
...（100+ 行 diff）
\`\`\`
```

### ✅ 正确方式（逻辑回档）

```markdown
## VER-20260807-001: 添加用户认证

### 为什么这么设计？
- 需求：用户需要安全登录
- 考虑方案：
  - A: Session + Cookie（简单但不支持多端）
  - B: JWT Token（支持多端，选择此方案）
  - C: OAuth2（过度设计，未来考虑）
  
### 关键取舍
- 选择 JWT：支持移动端和 Web 端
- 放弃 Session：避免服务器状态
- Token 过期时间：24小时（平衡安全和体验）

### 影响范围
- 新增：auth/ 模块
- 修改：API 所有端点增加认证中间件
- 消费者：前端需要在 header 中携带 token

### 验证方式
- 单元测试：tests/auth/jwt.test.js
- 集成测试：tests/api/auth-flow.test.js

### 回滚方式
- 移除 auth 中间件
- 前端回退到无认证版本
```

## logic_readme.md 的精简原则

**当前制度文档（logic_readme.md）只保留最新有效规则：**

```markdown
# 当前规则

| rule_id | 规则 | why | 决策记录 |
|---------|------|-----|----------|
| RULE-001 | 使用 JWT 认证 | 支持多端 | [VER-20260807-001](logic_version/records/...) |

❌ 不要保留：
- 旧的 Session 认证方案（已废弃）
- 考虑过但未采用的 OAuth2 方案
- 历史变更过程
```

**如果需要回忆历史，通过链接查看 VER-* 记录。**

## 代码地图与 Recall 的配合

- 代码地图回答"现在有哪些边界、入口、数据流、权威来源和测试入口"，用于从受影响路径定位到应读的代码与规则
- Recall 回答"为什么选择当前规则、改动会影响谁、哪些取舍已经确认"，用于避免只修当前表象而破坏既有约束

先用代码地图定位范围，再读取该范围的现行规则和活跃议案。只有高风险、规则直接引用或兼容性判断需要时，按 ID 读取对应的 ADR 或 `VER-*` 历史记录。

代码图谱或搜索结果只能说明关联，不能替代真实消费者、决策记录或运行证据。
