# 逻辑回档 vs 代码回档

**Recall 用现行文档说明当前规则，用历史留档记录修改及必要理由；代码版本交给 Git。**

## 基本区分

- **现行文档**：保存当前规则、必要理由与约束，供日常修改读取。
- **修改议案**：保存本任务拟议变化、当前进展及剩余工作。
- **历史留档**：保存改了什么、必要理由、取舍、影响与验证，查阅历史时按需读取。

## 为什么这样设计？

1. **避免上下文爆炸**：完整历史代码会让文档迅速膨胀，AI 无法有效读取
2. **Git 已经负责代码版本**：Recall 留档变更摘要和必要理由，不复制源码。
3. **现行文档足以指导修改**：必要约束及理由应归入所属 readme，不依赖历史补丁拼接。

## 历史记录保存什么？

`logic_version/records/` 中的 `logic_version-*` 记录保存：

**✅ 保存（轻量）：**
- 修改了什么？（变更摘要）
- 为什么做这个决策？（设计原因）
- 考虑过哪些方案？（A/B/C 对比）
- 为什么选择当前方案？（取舍分析）
- 影响了哪些消费者？（影响范围）
- 如何验证和回滚？（验证方式）

**❌ 不保存（避免膨胀）：**
- 完整的代码快照
- 逐行的代码变更 diff
- 详细的实现细节
- 原始对话记录（太长）
- 思维推理过程（隐藏思维链）

## 示例对比

### ❌ 错误方式（代码回档）

```markdown
## VER-20260807-001: 添加用户认证

### 代码快照
\`\`\`javascript
// 保存 500 行完整代码...
function authenticate(user, password) { ... }
\`\`\`

### 代码变更
\`\`\`diff
+ line 1: import jwt from 'jsonwebtoken'
+ line 2: import bcrypt from 'bcrypt'
...（100+ 行 diff）
\`\`\`
```

### ✅ 正确方式（逻辑回档）

```markdown
## VER-20260807-001: 添加用户认证

### 为什么这么设计？
- 需求：用户需要安全登录
- 考虑方案：
  - A: Session + Cookie（简单但不支持多端）
  - B: JWT Token（支持多端，选择此方案）
  - C: OAuth2（过度设计，未来考虑）
  
### 关键取舍
- 选择 JWT：支持移动端和 Web 端
- 放弃 Session：避免服务器状态
- Token 过期时间：24小时（平衡安全和体验）

### 影响范围
- 新增：auth/ 模块
- 修改：API 所有端点增加认证中间件
- 消费者：前端需要在 header 中携带 token

### 验证方式
- 单元测试：tests/auth/jwt.test.js
- 集成测试：tests/api/auth-flow.test.js

### 回滚方式
- 移除 auth 中间件
- 前端回退到无认证版本
```

## logic_readme.md 的精简原则

**当前制度文档（logic_readme.md）只保留最新有效规则：**

```markdown
# 当前规则

| rule_id | 规则 | why | 决策记录 |
|---------|------|-----|----------|
| RULE-001 | 使用 JWT 认证 | 支持多端 | [VER-20260807-001](logic_version/records/...) |

❌ 不要保留：
- 旧的 Session 认证方案（已废弃）
- 考虑过但未采用的 OAuth2 方案
- 历史变更过程
```

**只有任务明确要求查阅历史时，才通过链接查看 VER-* 记录（RULE-003）。**

## 代码地图与 Recall 的配合

- 代码地图回答"现在有哪些边界、入口、数据流、权威来源和测试入口"，用于从受影响路径定位到应读的代码与规则
- Recall 回答"为什么选择当前规则、改动会影响谁、哪些取舍已经确认"，用于避免只修当前表象而破坏既有约束

先按根文档与 `recall route` 定位范围，读取命中领域的现行规则、相关活跃议案及代码地图。历史读取沿用 RULE-003；高风险、历史链接或兼容判断本身不触发读取。

代码图谱或搜索结果只能说明关联，不能替代现行规则、真实消费者或运行证据。
