## 使用指南

### VER 记录应该保存什么？

✅ **应该保存：**
- 核心决策逻辑："为什么这么设计"
- 方案对比：考虑过哪些方案、为何选择/拒绝
- 关键约束：不可破坏的边界
- 影响范围：改变了什么公共契约

❌ **不应该保存：**
- 详细的测试输出（"SHA256: xxx"）
- 完整的代码片段（代码在 Git 里）
- 具体的测试命令（"npm test"）
- 冗长的实施细节（migration 脚本在代码库）

### 篇幅控制

- **目标长度**: 50-150 行
- **最大长度**: 不超过 200 行
- **核心原则**: 5 年后的维护者能快速理解"当时为什么这么做"

### 示例对比

**❌ 过度详细（不好）：**
```markdown
## 验证证据
- 测试输出：
  ```
  ✓ should lock source on import (23ms)
  ✓ should reject duplicate import (15ms)
  ...（30+ 行测试输出）
  ```
- SHA256 哈希：c1f717e23a1d555d797747b908327aaa07033e5d1193f197a04c5ac3137fe94c
- 具体测试命令：npm --prefix server test -- --grep "studio"
```

**✅ 恰当精简（好）：**
```markdown
## 验证方式
- 原子性测试：两个并发初始化最多一个成功
- 幂等性测试：同键同输入返回同一结果
- 真实环境：ECS migration 预检、备份恢复、微信真机通过
```
