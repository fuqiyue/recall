## 二、核心问题分析

### 问题 1：上下文膨胀

**现状：**
```
logic_change.md: 877 行
├─ 文档控制 + 索引: ~43 行
└─ 10 个 CHG 议案: ~834 行
   └─ 平均每个: ~83 行
```

但实际内容密度极高，包含：
- 30+ 个元数据字段（proposal_revision, decision_gate, semantic_review_state...）
- 完整的测试矩阵（30+ 行）
- 详细的验证证据（SHA256、测试输出）
- 冗长的 intent_digest、implementation_guard

**根本原因：**
没有严格区分"临时工作信息"和"永久决策记录"。CHG 应该是轻量的工作台，但实际变成了详尽的档案。

### 问题 2：逻辑与代码细节混杂

**典型例子（来自实际文档）：**

❌ **不应该出现在逻辑文档中：**
```markdown
- 活动首页 SHA256 c1f717e23a1d555d797747b908327aaa07033e5d1193f197a04c5ac3137fe94c
- 测试输出：pass:16/16, pass:9/9, pass:2/2
- 测试命令：npm --prefix server test -- --grep "studio"
- 代码路径：server/src/studio/studio-service.js:123-456
```

✅ **应该保存的逻辑：**
```markdown
**为什么导入即锁定：**
1. 防止上下文混合 — 模型对话基于固定来源
2. 避免并发问题 — 原子初始化比"首次回答后锁"简单
3. 明确用户意图 — 显式新建比静默切换清楚
```

### 问题 3：历史信息未归档

**现状：**
- 已确认的 revision 仍保留所有历史 revision 信息
- prior_confirmation、semantic_review_ref 等字段堆积
- 决策过程的完整记录（confirmation_request, prior_confirmation）

**应该做：**
- revision 确认后，只保留当前 revision 的关键信息
- 历史 revision 的详细记录移到 logic_version/

## 三、优化策略

### 策略 1：精简 CHG 元数据（30+ → 10 个核心字段）

**保留：**
- status, revision, 确认信息, created, reserved_version_id
- 当前状态、阻塞因素、下一步行动

**移除：**
- 所有 prior_* 字段（移到 VER）
- 详细的 authority_surfaces（在代码地图中已存在）
- 冗长的 intent_digest、implementation_guard
- 完整的测试矩阵和验证证据

### 策略 2：CHG 聚焦"当前工作状态"

**CHG 的核心问题：**
1. 这个议案想做什么？（目标）
2. 为什么这么做？（3-5 条核心理由）
3. 当前在哪里？（已完成 vs 阻塞）
4. 下一步做什么？（具体行动）

**CHG 不应该包含：**
- 完整的实施细节（在代码里）
- 详细的测试输出（在 CI 日志里）
- 历史决策过程（在 VER 里）

### 策略 3：VER 聚焦"决策逻辑"

**VER 的核心问题：**
1. 解决什么问题？
2. 考虑过哪些方案？
3. 为什么选择这个方案？
4. 关键约束是什么？
5. 如何验证和回滚？

**VER 不应该包含：**
- 代码片段（在 Git 里）
- 测试输出（在测试套件里）
- SHA256 哈希（在构建系统里）

### 策略 4：分离技术证据

**建议：**
创建独立的 `technical_evidence/` 目录：
```
technical_evidence/
├─ CHG-20260725-001/
│  ├─ test-output.txt
│  ├─ migration-validation.log
│  └─ browser-screenshots/
└─ CHG-20260724-003/
   ├─ smoke-test-results.txt
   └─ oauth-flow-trace.log
```

logic_*.md 只链接，不内嵌。

## 五、是否能保持项目整洁和逻辑清晰？

### ✅ 理念层面：完全正确

Recall 系统的核心理念非常优秀：
- **逻辑回档 vs 代码回档** — 保存设计推理，不保存代码快照
- **单一真源** — logic_readme.md 是当前规则唯一来源
- **版本化决策** — 历史决策归档到 logic_version/
- **三层修改通道** — simple/medium/high-risk 决策门槛

### ❌ 实际执行：偏离了原则

**主要问题：**
1. **没有严格执行"逻辑 vs 代码"分离**
   - 保存了大量测试输出、SHA256、具体命令
   - 这些应该在代码库、CI 系统和构建产物中

2. **CHG 变成了"完整档案"而非"工作台"**
   - 应该：轻量、临时、聚焦当前状态
   - 实际：详尽、永久、包含所有历史

3. **缺乏自动清理机制**
   - CHG 完成后应该精简为 VER
   - 但实际上完整保留了所有细节

### 🔧 改进后的预期效果

**如果按优化建议执行：**

✅ **项目整洁度：**
- logic_change.md 压缩 70%+
- 活跃议案一目了然
- 技术细节外置到 technical_evidence/

✅ **逻辑清晰度：**
- CHG 清楚显示"在做什么、为什么、当前状态"
- VER 清楚显示"当时为什么这么决策"
- 5 年后的维护者能快速理解设计推理

✅ **可维护性：**
- 新议案按模板创建，不会膨胀
- 完成的议案自动提炼为精简 VER
- 核心原则得到执行
